# 2단계: 한글·말본 나래(문법·어휘) 설계

작성: 2026-11-03 (계획·검수 Opus, 구현 Sonnet — `CLAUDE.md` 작업 분담)

## 원칙

1. **AI 없이 규칙으로 채점**: 문법 문제는 정답 규칙이 분명하다. 비용 0, 오프라인 동작, 오판 위험 없음.
2. **찍기 방지(원리 → 재시도)**: 틀리면 정답 대신 원리를 생각하게 하는 말. 2번째 오답에 힌트 1, 3번째에 힌트 2, 4번째에 정답과 설명을 보여 주고 '도움 받아 완료'로 기록. 학생을 탓하는 말은 쓰지 않는다.
3. **드래그 없는 조작(UDL)**: 블록을 '누르고 → 놓을 칸 누르기'. 키보드로도 조작 가능.
4. **모든 문제는 성취기준 코드에 묶는다**(`src/core/data/standards.ts`).
5. **연구 데이터**: 문제별 시도 횟수, 힌트 사용, 정답까지 걸린 시간, '도움 받아 완료' 여부를 기록.

### 문제 형식

- **sentence-build**: 낱말 블록(역할: 누가/무엇이, 무엇을, 어떻게(꾸며 주는 말), 어찌하다/어떠하다/무엇이다)을 순서대로 놓아 문장을 만든다. 국어는 어순이 비교적 자유로우므로 자연스러운 순서를 모두 정답 목록에 넣는다.
- **agreement-fix**: 어절로 나뉜 문장에서 ① 어색한 어절을 고르고 ② 바른 표현을 보기에서 고른다. 두 단계 모두 맞아야 정답.
- **choice**: 문장(`context`)의 낱말(`target`, 굵게 표시)이나 낱말 묶음에 대해 보기 3~4개 중 하나를 고른다. 정답 자리(`correctOption`)·설명·힌트는 학생 기기로 보내지 않는다. 띄어쓰기 문제(agreement-fix)는 띄어쓰기가 틀린 덩어리가 한 어절이고, 정답 보기에 띄어쓰기가 들어 있다(예: 어절 `할수있어요.` → 보기 `할 수 있어요.`).

## 단계

1. **핵심부**(`src/core/grammar/`): 형식·채점·힌트 규칙·문제 은행·검증, 단위 테스트. ← 첫 구현 지시서
2. **앱 연결**: 과제 종류(글쓰기/문법) 추가와 DB 마이그레이션, 교사 과제 생성, 학생 활동 화면, 교사 결과 화면(문제별 정답률·힌트 사용), 연구용 CSV, 브라우저 시험.
3. 2차(구현·검수 완료): 다의어·낱말 관계([4국04-01]), 국어사전 기본형([4국04-02]), 시간 표현([6국04-05]), 맞춤법·띄어쓰기([6국04-06], 1단계 점검기 재사용).

## 검수 기준(Opus)

- 문제 내용의 문법적 정확성은 **문제 하나하나 직접 읽고** 확인한다(구현 담당이 쓴 문제 포함).
- 정답 목록이 자연스러운 어순을 빠뜨리지 않았는지, 보기 중 정답이 둘 이상인 문제가 없는지 확인한다.
- 학생에게 보이는 문구(피드백·힌트)가 해요체이고 학생을 탓하지 않는지 확인한다.

### 연구 데이터 해석 시 주의

- **첫 시도 정답**: 첫 시도가 '어색한 순서'(오답으로 세지 않음)였어도 첫 시도 정답이 아닌 것으로 센다. 어순 문제의 첫 시도 정답률이 낮으면 시도 기록(grammar_attempts.reason = "awkward")을 함께 확인한다.
- **max_hint_level**: 0 없음(원리 안내만 본 경우 포함), 1 힌트1, 2 힌트2, 3 정답 공개(도움 받아 완료).
- **seconds_to_solve**: 그 문제의 첫 시도부터 푼 시도까지(문제를 처음 본 시각이 아님).
