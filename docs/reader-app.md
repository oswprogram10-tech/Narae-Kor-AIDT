# 국어나래 낭독 도우미(윈도우 앱) 설계

작성: 2026-11-10 (계획·검수 Opus, 구현 Sonnet — `CLAUDE.md` 작업 분담)

## 왜 따로 앱을 두나

브라우저 안(WebAssembly)에서는 CPU의 빠른 명령어·여러 코어·GPU를 다 쓰지 못하고, 메모리도 4GB까지라서 음성 인식 2·3단계가 느리다. 설치형 앱은 같은 모델을 **기기 안에서 그대로** 돌리되 CPU를 제대로 쓰고, **DirectML로 NVIDIA·AMD·Intel 그래픽(내장 포함)**을 쓸 수 있다.

- 학생 기기: 설치 없이 브라우저 1단계(그대로).
- 교사 윈도우 노트북·GPU PC: 이 앱으로 2·3단계를 빠르게. 학생은 교사 기기 앞에서 읽는다.

## 원칙(지금까지 결정과 같음)

1. **목소리는 기기 밖으로 나가지 않는다.** 녹음은 메모리에서만 인식에 쓰고 디스크에 저장하지 않는다. 앱의 네트워크는 (a) 국어나래 웹 서버, (b) 모델 파일을 내려받는 학교(국내) 서버 두 곳만 허용하고 나머지는 막는다. 음성 데이터를 담은 요청은 어디로도 보내지 않는다.
2. 결과는 '진단'이 아니라 **연습 참고 지표**(1분에 바르게 읽은 어절 수, 다시 읽어 볼 곳). 서버에는 숫자 결과만 저장할 수 있다(전사 글·음성 없음).
3. 낭독 기능은 **기본 꺼짐**. 교사가 학급 단위로 켤 때 "학교장 승인과 보호자 동의를 받았어요" 확인을 거치고, 동의한 학생만 쓸 수 있다(교사가 학생별로 표시). 동의하지 않은 학생은 같은 글을 읽고 스스로 체크하는 대체 활동.
4. 모델 파일에는 출처 표시(NIA)·라이선스(Whisper MIT) 문구를 함께 둔다.

## 구조

**Electron 앱 하나 + 웹 모듈 재사용 + 기기 안 인식 엔진**

```
[국어나래 웹 화면(기존 Next.js)]  ← 앱 창 안에 그대로 띄움
        │  window.naraeSpeech (preload로 노출한 좁은 API)
        ▼
[앱 메인 프로세스] ── 네트워크 허용 목록(웹 서버, 모델 서버만)
        │
        ▼
[인식 전용 프로세스(utility process)]
   transformers.js + onnxruntime-node
   장치: DirectML(GPU) → 안 되면 CPU(여러 코어)
   모델: 브라우저와 같은 ONNX(q8 / fp16) 파일
```

- **모델 형식은 브라우저와 하나로 통일**한다(`training/asr/export_asr.py`가 만드는 transformers.js 형식). 그래서 학습·내보내기·평가 도구를 그대로 쓰고, 같은 모델이 브라우저(1단계)와 앱(2·3단계)에서 돈다.
- 웹 화면은 `window.naraeSpeech`가 있으면 앱 엔진을, 없으면 브라우저 엔진(1단계)을 쓴다(`src/core/speech`의 공통 형식).
- 엔진을 별도 프로세스에 두어 인식 중에도 화면이 멈추지 않는다.

### `window.naraeSpeech` (좁은 API)
- `info()` → 앱 버전, CPU 코어, RAM, 쓸 수 있는 장치(directml/cpu), 그래픽 이름·메모리(가능한 범위)
- `models()` → 단계별 모델과 설치 여부, 크기
- `install(modelId)` → 학교 서버에서 받기(진행률), `manifest.json`의 sha256 확인 후에만 사용
- `remove(modelId)`
- `transcribe(audio16k: Float32Array, { modelId, device? })` → `{ text, seconds, rtf, device }` (음성은 이 호출 안에서만 쓰고 버림)
- `benchmark(modelId)` → 짧은 합성 입력으로 1분 낭독 처리 시간 어림(녹음 없이)

renderer에는 Node 기능을 주지 않는다(`contextIsolation`, `sandbox`, `nodeIntegration: false`). 앱 창은 허용한 웹 서버 주소만 연다.

## 단계

1. **시험판(지금)**: 앱 뼈대, 인식 엔진 프로세스, 모델 설치·확인, `transcribe`·`benchmark`, 간단한 '속도 시험' 화면(앱 안 자체 화면: 모델 고르기 → 장치 고르기 → 1분 낭독 처리 시간 비교: CPU vs DirectML, 브라우저 엔진과 비교). 설치 파일(NSIS) 설정. 목적: **5625U에서 앱 방식이 실제로 얼마나 빠른지 재기.**
2. **낭독 화면(웹 쪽)**: 학급별 켜기·동의 표시, 낭독 글(자체 창작, 학년별), 녹음 → 인식 → `src/core/fluency` 채점 → 다시 읽어 볼 곳 표시, 숫자 결과만 저장, 교사 현황. 앱과 브라우저 둘 다에서 동작.
3. 교사 판정 화면(같은 낭독을 교사가 듣고 체크) → 기계·교사 일치도 연구 데이터.
4. 배포: 코드 서명, 자동 업데이트(학교 서버), 설치 안내서.

## 알려진 위험

- 학교 기기 설치 권한·보안 정책(교육청 심사)이 필요할 수 있다.
- DirectML 성능은 그래픽마다 차이가 크다 → 앱이 처음 실행 때 장치별로 재서 빠른 쪽을 고른다.
- 이 개발 환경(리눅스 클라우드)에서는 윈도우·DirectML을 시험할 수 없다. CPU 경로는 리눅스 Electron/Node로 시험하고, 윈도우 실측은 사용자 노트북(5625U)에서 한다.
