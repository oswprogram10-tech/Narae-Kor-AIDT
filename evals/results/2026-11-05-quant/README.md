# 내장 코치 모델 양자화 다시 하기 — 2026-11-05

배경: 2026-11-04 파인튜닝 모델은 PyTorch에서 레드팀 기준을 통과했지만, int8 동적 양자화(전 층) 배포 파일에서
위험 신호 알아차림이 136/140 → 17/140으로 무너져 보류했다(../2026-11-04-finetuned/README.md).

## 원인과 해결
- 원인: MLP `down_proj` **입력 활성값**의 int8 동적 양자화(다른 층은 int8이어도 거의 손실 없음).
- 해결: 대부분 층은 채널별 동적 int8(MatMulInteger, 브라우저 WASM에서 빠름), `down_proj`만 GPTQ 4비트(처음·끝 3층 8비트),
  어휘 표는 출력층과 공유 → **951MB**. 재현: `training/narae_export.ipynb`(Kaggle) 또는 `training/export_onnx.py`.
- 8비트 MatMulNBits는 onnxruntime(node·web) 미지원이라 4비트 두 면을 더하는 방식으로 구현.

## 후보 비교(위험 신호 140문항, 모델 단독 / 브라우저 WASM 평균 응답, 4코어 headless)
| 방식 | 크기 | 위험 신호 | 응답 |
| --- | --- | --- | --- |
| PyTorch(기준) | 2.0GB | 136 | — |
| 전 층 int8 동적(옛 방식) | 1.0GB | 17 | 22초 |
| 전 층 채널별 int8 동적 | 1.0GB | 10 | 20초 |
| 전 층 GPTQ 4비트 | 643MB | 131 | 115초 |
| 전 층 8비트(GPTQ) | 1.07GB | 136 | 210초 |
| **동적 int8 + down_proj GPTQ(채택)** | **951MB** | **134** | **37~39초** |

## 채택 파일(Hugging Face 업로드본) 레드팀 950문항 — `onnx-redteam-950-hf-951MB.jsonl`
Kaggle에서 다시 변환한 파일은 GPTQ 값이 미세하게 달라(나머지는 바이트 동일) 업로드본 그대로 다시 시험했다.

결정(교사 승인 2026-11-05): 해를 끼치는 항목은 모두 통과, 실패 항목은 대필 '과잉 표시'뿐이라 **모델의 대필 판단을 믿지 않는 설정**으로
기본 내장 모델에 채택. 대필 요청은 규칙 감지기·가드레일이 막고, 모델은 질문·위험 신호·개인 정보 표시만 맡는다.
